01

Control de Acceso

RUID, EUID y setuid — ¿quién soy para el kernel?

Cada proceso lleva asociados varios identificadores de usuario. Los más importantes son:

RUID — Real User ID

El usuario que lanzó el proceso. No cambia durante la vida del proceso (salvo llamadas privilegiadas). El kernel lo usa para enviar señales: solo puedes matar procesos cuyo RUID coincida con el tuyo (o ser root).

EUID — Effective User ID

El usuario que el kernel comprueba para acceder a recursos (ficheros, sockets…). Normalmente EUID = RUID, pero cuando se activa el setuid bit, el EUID se convierte en el UID del dueño del ejecutable.

Ejemplo práctico: passwd

El ejecutable /usr/bin/passwd tiene el bit setuid activo (-rwsr-xr-x, dueño: root). Cuando un usuario normal lo ejecuta:

  • RUID = UID del usuario (ej. 1001) — sigue siendo "yo"
  • EUID = 0 (root) — el proceso actúa con permisos de root
  • Así puede escribir en /etc/shadow (solo root) aunque lo lance cualquier usuario
# Ver setuid en un binario
ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root  # 's' en lugar de 'x' = setuid activo

chmod u+s /ruta/binario   # activar setuid
chmod 4755 /ruta/binario  # equivalente octal
⚠️
Riesgo de seguridad: un binario con setuid mal programado puede ser explotado para escalar privilegios. Usar con mucha cautela y solo cuando sea estrictamente necesario.

setgid y sticky bit

chmod g+s directorio   # setgid: ficheros nuevos heredan el grupo del dir
chmod 2755 directorio
chmod +t /tmp          # sticky: solo el dueño puede borrar sus ficheros
chmod 1777 /tmp

Login shell vs nologin shell

Login shell

El usuario puede iniciar sesión interactiva en el sistema. El campo shell de /etc/passwd apunta a un intérprete real como /bin/bash, /bin/zsh, /bin/sh.

Al hacer login se ejecutan los ficheros de inicialización (/etc/profile, ~/.bashrc…).

usuario:x:1001:1001::/home/usuario:/bin/bash

nologin shell

El usuario no puede iniciar sesión. Se usa para cuentas de servicio (www-data, postgres, daemon…) que necesitan existir como propietarios de procesos/ficheros pero no deben tener acceso interactivo.

El campo shell apunta a /usr/sbin/nologin o /bin/false. Si alguien intenta conectarse, recibe un mensaje de denegación y la sesión se cierra.

www-data:x:33:33::/var/www:/usr/sbin/nologin
# Cambiar shell de un usuario
chsh -s /usr/sbin/nologin usuario   # desactivar login
chsh -s /bin/bash usuario           # reactivar login
usermod -s /usr/sbin/nologin usuario

Shadow: formato del hash de contraseña

Las contraseñas nunca se guardan en texto plano. En /etc/shadow se almacena un hash con este formato:

$id$salt$hash

Ejemplo real:
$6$rounds=5000$saltaleatorio$ABCDEFxyz...
Identificador $id$AlgoritmoEstado
$1$MD5Obsoleto
$2a$ / $2b$bcryptSeguro
$5$SHA-256Aceptable
$6$SHA-512Recomendado en Linux
$y$yescryptModerno, Debian 11+

El salt es una cadena aleatoria que se añade antes de hashear. Su función es que dos usuarios con la misma contraseña tengan hashes distintos, y que los ataques de diccionario con tablas precomputadas (rainbow tables) sean ineficaces.

# Generar hash SHA-512 manualmente
mkpasswd -m sha-512 -S "saltaleatorio" "micontraseña"
python3 -c "import crypt; print(crypt.crypt('pass', crypt.mksalt(crypt.METHOD_SHA512)))"

Criptografía

Los 3 pilares de la seguridad criptográfica

🔒 Confidencialidad

Nadie que intercepte los datos puede leerlos. Se consigue con cifrado simétrico (AES) o asimétrico (RSA).

✅ Integridad

Los datos no han sido modificados en tránsito. Se verifica con funciones hash (SHA-256): si un bit cambia, el hash es completamente distinto.

🪪 Autenticación

Se puede probar quién envió el mensaje. Se consigue con firmas digitales (clave privada) verificables por cualquiera con la clave pública.

Criptografía Simétrica vs Asimétrica

SimétricaAsimétrica
Claves1 clave compartida (cifra y descifra)Par: clave pública + privada
VelocidadMuy rápida~1000× más lenta
ProblemaDistribución segura de la claveNo escala para grandes volúmenes
AlgoritmosAES-256, ChaCha20RSA-4096, ECC, Ed25519
Uso en TLSCifrado de datos de sesiónIntercambio de clave de sesión

Stream ciphers (RC4 — obsoleto): cifran bit a bit. Block ciphers (AES): cifran bloques de 128 bits con la misma clave → mismo bloque de entrada produce mismo bloque de salida (requiere modo de operación como CBC, GCM).

Hash y PKI

Las funciones hash son unidireccionales: fácil calcular H(x), imposible obtener x a partir de H(x). Algoritmos: MD5 (roto), SHA-256, SHA-512.

La PKI (Public Key Infrastructure) gestiona certificados digitales que asocian una clave pública a una identidad, firmados por una CA (Certificate Authority).

Flujo HTTPS: servidor envía certificado → cliente verifica firma de la CA → se usa criptografía asimétrica para intercambiar una clave de sesión → resto de la comunicación con AES.

SSH — Clave pública/privada: configuración completa

La autenticación por clave pública es más segura que por contraseña: el servidor solo almacena la clave pública (no hay secreto que robar del servidor).

Paso 1 — Generar el par de claves (en el cliente)

# Ed25519: recomendado (más corto, igual de seguro que RSA-4096)
ssh-keygen -t ed25519 -C "comentario@maquina"

# RSA clásico (compatible con sistemas más antiguos)
ssh-keygen -t rsa -b 4096 -C "comentario"

# Resultado:
~/.ssh/id_ed25519      # clave PRIVADA — NUNCA compartir
~/.ssh/id_ed25519.pub  # clave PÚBLICA — se copia al servidor

Paso 2 — Copiar la clave pública al servidor

# Método automático (recomendado)
ssh-copy-id -i ~/.ssh/id_ed25519.pub usuario@servidor
# → añade la clave a ~/.ssh/authorized_keys en el servidor

# Método manual
cat ~/.ssh/id_ed25519.pub | ssh usuario@servidor \
  "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys"

Paso 3 — Permisos obligatorios

chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519         # clave privada: SOLO el propietario
chmod 644 ~/.ssh/id_ed25519.pub
chmod 600 ~/.ssh/authorized_keys

Paso 4 — Conectar y opciones avanzadas

ssh usuario@servidor                          # conexión básica
ssh -p 2222 usuario@servidor                  # puerto alternativo
ssh -i ~/.ssh/otra_clave usuario@servidor     # clave específica

# ~/.ssh/config — alias de conexiones
Host miservidor
    HostName 192.168.1.10
    User admin
    IdentityFile ~/.ssh/id_ed25519
    Port 22

ssh miservidor  # usa la config anterior

# ssh-agent: evitar escribir passphrase cada vez
eval $(ssh-agent)
ssh-add ~/.ssh/id_ed25519
💡
Deshabilitar autenticación por contraseña en /etc/ssh/sshd_config una vez configuradas las claves: PasswordAuthentication no. Así solo se puede entrar con clave.

iptables actúa sobre el subsistema Netfilter del kernel Linux. Los paquetes pasan por distintos hooks según su destino:

Entrada:   PREROUTING → INPUT (proceso local)
Reenvío:   PREROUTING → FORWARD → POSTROUTING
Salida:    OUTPUT → POSTROUTING
TablaPropósitoCadenas disponibles

natTraducción de direccionesPREROUTING, POSTROUTING, OUTPUT
mangleModificar cabeceras IP/TCPTodas
rawEvitar tracking de conexionesPREROUTING, OUTPUT

DROP vs REJECT — ¿cuándo usar cada uno?

DROP

El paquete se descarta silenciosamente. El emisor no recibe ninguna respuesta y tiene que esperar al timeout.

  • Ventaja: no revela que existe un firewall ni que el puerto está filtrado. Dificulta el fingerprinting.
  • Ventaja: ralentiza los escaneos automáticos (nmap, bots).
  • Inconveniente: las conexiones legítimas tardan más en fallar (esperan timeout).
  • Usar en: política por defecto (-P INPUT DROP), tráfico de Internet desconocido, protección contra escaneos.
iptables -P INPUT DROP         # política por defecto
iptables -A INPUT -j DROP      # al final de la cadena

REJECT

El paquete se descarta pero se envía de vuelta un mensaje de error ICMP (icmp-port-unreachable por defecto, o tcp-reset para TCP).

  • Ventaja: el cliente sabe inmediatamente que la conexión fue rechazada, sin esperar timeout. Mejor experiencia para usuarios legítimos.
  • Inconveniente: revela la existencia del firewall y que el puerto está activamente bloqueado.
  • Usar en: redes internas donde el feedback rápido es prioritario, reglas que afectan a usuarios conocidos.
iptables -A INPUT -p tcp --dport 23 \
  -j REJECT --reject-with tcp-reset
iptables -A INPUT -j REJECT \
  --reject-with icmp-port-unreachable
ℹ️
Regla general: usa DROP para la política por defecto y para tráfico externo/desconocido. Usa REJECT dentro de redes internas donde quieres que los fallos sean rápidos y explícitos.

NAT — Network Address Translation

NAT permite que múltiples máquinas de una red privada compartan una sola IP pública. Opera en la tabla nat de iptables.

SNAT — Source NAT

Cambia la IP origen de los paquetes salientes. Se usa cuando la IP pública es fija. Se aplica en POSTROUTING (después de decidir el enrutamiento).

iptables -t nat -A POSTROUTING \
  -o eth1 \
  -j SNAT --to-source 203.0.113.5
# eth1 = interfaz hacia Internet
# 203.0.113.5 = IP pública fija

MASQUERADE

Variante de SNAT para IPs dinámicas (DHCP). En lugar de especificar la IP, el kernel toma automáticamente la IP actual de la interfaz de salida. Más flexible pero ligeramente más lento.

iptables -t nat -A POSTROUTING \
  -o eth1 \
  -j MASQUERADE
# No necesita saber la IP pública
# Ideal para: routers domésticos, VPS con IP dinámica

DNAT — Destination NAT (Port Forwarding)

Cambia la IP/puerto destino. Redirige tráfico que llega a la IP pública hacia una máquina interna. Se aplica en PREROUTING (antes del enrutamiento).

# Redirigir puerto 80 externo → servidor web interno 10.1.1.2:80
iptables -t nat -A PREROUTING -i eth1 -p tcp --dport 80 \
  -j DNAT --to-destination 10.1.1.2:80

# También hay que permitir el FORWARD hacia el servidor interno
iptables -A FORWARD -d 10.1.1.2 -p tcp --dport 80 -j ACCEPT

# También hay que habilitar ip_forward en el kernel
sysctl -w net.ipv4.ip_forward=1
echo "net.ipv4.ip_forward=1" >> /etc/sysctl.d/99-routing.conf

Plantilla completa de firewall con NAT

# Limpiar reglas existentes
iptables -F; iptables -X; iptables -t nat -F

# Políticas por defecto
iptables -P INPUT DROP
iptables -P FORWARD DROP
iptables -P OUTPUT ACCEPT

# Tráfico stateful (siempre primero)
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A FORWARD -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A INPUT -m conntrack --ctstate INVALID -j DROP

# Loopback y red interna
iptables -A INPUT -i lo -j ACCEPT
iptables -A INPUT -i eth0 -j ACCEPT          # eth0 = red interna
iptables -A FORWARD -i eth0 -o eth1 -j ACCEPT

# NAT salida (Masquerade para IP dinámica)
iptables -t nat -A POSTROUTING -o eth1 -j MASQUERADE

# DNAT: port forwarding SSH al servidor interno
iptables -t nat -A PREROUTING -i eth1 -p tcp --dport 22 \
  -j DNAT --to-destination 10.1.1.10:22
iptables -A FORWARD -d 10.1.1.10 -p tcp --dport 22 -j ACCEPT

# Servicios permitidos desde exterior
iptables -A INPUT -p tcp --dport 22 -j ACCEPT
iptables -A INPUT -p icmp --icmp-type echo-request -j ACCEPT

# Persistir reglas
apt install iptables-persistent
iptables-save > /etc/iptables/rules.v4

nftables — Sintaxis moderna

# nftables unifica filter + nat en una sola herramienta
nft add table inet fw
nft add chain inet fw input { type filter hook input priority 0 \; policy drop \; }
nft add rule inet fw input ct state established,related accept
nft add rule inet fw input iifname "lo" accept
nft add rule inet fw input tcp dport 22 accept

# NAT con nftables
nft add table ip nat
nft add chain ip nat postrouting { type nat hook postrouting priority srcnat \; }
nft add rule ip nat postrouting oifname "eth1" masquerade

nft list ruleset           # ver todo
nft -f /etc/nftables.conf  # cargar fichero
systemctl enable --now nftables

APIPA — Automatic Private IP Addressing

APIPA es un mecanismo por el que un dispositivo se asigna automáticamente una dirección IP cuando no puede contactar con un servidor DHCP. El rango es 169.254.0.0/16 (definido en RFC 3927).

¿Cómo funciona?

  1. El dispositivo intenta obtener IP por DHCP (envía DHCP Discover en broadcast).
  2. Si no recibe respuesta tras varios intentos, selecciona aleatoriamente una dirección en 169.254.1.0 – 169.254.254.255.
  3. Antes de usarla, envía una petición ARP para verificar que nadie más la tiene (ARP probe). Si hay colisión, elige otra.
  4. Configura la interfaz con esa IP y máscara /16.

Limitaciones importantes

  • Solo funciona en la misma red local: no hay gateway, no hay DNS, no hay acceso a Internet.
  • Útil para diagnóstico y comunicación directa entre máquinas en la misma LAN sin infraestructura.
  • Ver una IP APIPA en producción indica un problema con el servidor DHCP o la red.
# Detectar si una interfaz tiene IP APIPA
ip a | grep "169.254"
# Si aparece → revisar: ¿está el DHCP server activo? ¿hay conectividad?

Configuración de red: estática vs dinámica

IP Estática

La IP se configura manualmente y no cambia. Recomendada para servidores, routers, impresoras de red y cualquier dispositivo al que otros se conecten por IP.

Ventaja: siempre la misma dirección. Inconveniente: hay que configurar manualmente cada dispositivo.

IP Dinámica (DHCP)

Un servidor DHCP asigna la IP automáticamente. Recomendada para clientes (PCs, laptops, móviles).

Ventaja: gestión centralizada, sin configuración manual. Inconveniente: la IP puede cambiar.

Configurar IP estática con ip (temporal, no persiste al reiniciar)

ip addr add 192.168.1.10/24 dev eth0
ip link set eth0 up
ip route add default via 192.168.1.1
echo "nameserver 8.8.8.8" > /etc/resolv.conf

Configurar IP estática con ifupdown (/etc/network/interfaces)

auto eth0
iface eth0 inet static
    address 192.168.1.10
    netmask 255.255.255.0
    gateway 192.168.1.1
    dns-nameservers 8.8.8.8 1.1.1.1

# Aplicar cambios
ifdown eth0 && ifup eth0

Configurar IP estática con NetworkManager (nmcli)

# Crear conexión con IP estática
nmcli con add type ethernet con-name "mi-red" ifname eth0 \
  ip4 192.168.1.10/24 gw4 192.168.1.1
nmcli con mod "mi-red" ipv4.dns "8.8.8.8 1.1.1.1"
nmcli con mod "mi-red" ipv4.method manual
nmcli con up "mi-red"

# Ver estado de conexiones
nmcli con show; nmcli dev status

Configurar IP dinámica (DHCP)

# Con ip (iniciar cliente DHCP manualmente)
dhclient eth0

# Con ifupdown
iface eth0 inet dhcp   # en /etc/network/interfaces

# Con nmcli
nmcli con mod "mi-red" ipv4.method auto
nmcli con up "mi-red"

Boot / Shutdown

Fases del arranque Linux

1. POST (Power-On Self Test)

El firmware comprueba que el hardware básico funciona (CPU, RAM, teclado…). Si algo falla, emite pitidos o muestra error.

2. BIOS / UEFI

Localiza el dispositivo de arranque y carga el bootloader. Ver tabla comparativa abajo.

3. GRUB

Carga el kernel e initrd. Muestra menú de arranque. Ver sección GRUB.

4. Kernel

Descomprime vmlinuz, monta initrd como rootfs temporal, detecta hardware, carga drivers básicos, arranca PID 1.

5. systemd (PID 1)

Gestiona el resto del arranque: monta filesystems, inicia servicios según dependencias, activa targets.

6. Espacio de usuario

Se completa el target por defecto (graphical.target o multi-user.target). El usuario puede hacer login.

GRUB — ¿Por qué no lo sustituye UEFI?

UEFI puede cargar directamente un kernel Linux firmado sin GRUB (usando EFI stub). Sin embargo, GRUB sigue siendo imprescindible porque:

  • Menú de arranque multi-sistema: GRUB gestiona arranque dual (Linux + Windows) con un menú visual.
  • Parámetros del kernel en tiempo real: se pueden editar antes de arrancar (modo rescate, init=/bin/bash…).
  • Compatibilidad: funciona tanto con BIOS como con UEFI.
  • Múltiples kernels: permite seleccionar entre versiones instaladas del kernel.
update-grub                             # regenerar /boot/grub/grub.cfg
grub-mkconfig -o /boot/grub/grub.cfg   # equivalente
cat /proc/cmdline                       # parámetros con los que arrancó el kernel actual
journalctl -k                           # mensajes del kernel (dmesg persistente)

Versiones de paquetes — significado

Los paquetes siguen el esquema de Versionado Semántico (SemVer):

v1.4.2-3~ubuntu22.04
 │  │  │  │   └── Sufijo de distribución (no afecta compatibilidad)
 │  │  │  └────── Revisión del paquete (cambios en el empaquetado, no en el código)
 │  │  └───────── PATCH: corrección de bugs, totalmente compatible
 │  └──────────── MINOR: nueva funcionalidad, compatible hacia atrás
 └─────────────── MAJOR: cambios incompatibles con versiones anteriores
  • Cambio de MAJOR (1→2): puede romper scripts o configuraciones existentes. Requiere revisión.
  • Cambio de MINOR (1.3→1.4): nuevas funciones, pero lo que funcionaba antes sigue funcionando.
  • Cambio de PATCH (1.4.1→1.4.2): solo correcciones. Actualizar siempre.
# Ver versión instalada y disponible
apt-cache policy nginx
dpkg -l nginx

dpkg vs APT — diferencias clave

dpkg — bajo nivel

Herramienta de bajo nivel. Trabaja con ficheros .deb individuales. No accede a repositorios ni resuelve dependencias automáticamente.

dpkg -i paquete.deb     # instalar .deb local
dpkg -r paquete         # desinstalar
dpkg -l                 # listar instalados
dpkg -L paquete         # ficheros del paquete
dpkg -S $(which cmd)    # qué paquete tiene ese fichero
dpkg --get-selections   # todos los paquetes

APT — alto nivel

Herramienta de alto nivel. Usa dpkg internamente pero además: accede a repositorios remotos, descarga paquetes, resuelve dependencias automáticamente, verifica firmas GPG.

apt update              # actualizar lista repos
apt install paquete     # instalar + deps
apt remove paquete      # eliminar
apt purge paquete       # eliminar + config
apt upgrade             # actualizar todo
apt autoremove          # limpiar huérfanos
apt search kw           # buscar en repos
apt-file search fichero # qué paquete lo incluye
ℹ️
Repositorios: configurados en /etc/apt/sources.list y /etc/apt/sources.list.d/*.list. Cada entrada tiene: tipo (deb/deb-src), URL, distribución y componentes (main contrib non-free).

Verificación por firma GPG en APT

APT verifica la autenticidad de los paquetes mediante criptografía de clave pública. El mantenedor del repositorio firma los metadatos con su clave privada GPG, y APT los verifica con la clave pública.

# Flujo de verificación:
# 1. apt update descarga Release + Release.gpg del repositorio
# 2. APT verifica Release.gpg con las claves en /etc/apt/trusted.gpg.d/
# 3. Release contiene checksums SHA256 de todos los ficheros del repo
# 4. Cada .deb descargado se verifica contra esos checksums

# Añadir clave GPG de un repositorio externo (método moderno)
wget -qO- https://repo.ejemplo.com/KEY.gpg | \
  gpg --dearmor | \
  sudo tee /etc/apt/trusted.gpg.d/ejemplo.gpg > /dev/null

# Añadir el repositorio
echo "deb [signed-by=/etc/apt/trusted.gpg.d/ejemplo.gpg] \
  https://repo.ejemplo.com stable main" | \
  sudo tee /etc/apt/sources.list.d/ejemplo.list

# Ver claves de confianza
apt-key list    # (obsoleto pero aún funciona)
ls /etc/apt/trusted.gpg.d/

Módulos del kernel — carga en caliente

Linux tiene un diseño modular: el kernel base es pequeño y carga drivers/funcionalidades adicionales como módulos en tiempo real, sin reiniciar. Esto permite añadir soporte para nuevo hardware, protocolos de red o sistemas de ficheros de forma dinámica.

uname -r                   # versión del kernel actual
lsmod                      # módulos cargados (nombre, tamaño, nº de usos)
modinfo e1000              # info de un módulo: deps, parámetros, descripción

modprobe nombre            # cargar módulo (resuelve dependencias automáticamente)
modprobe -r nombre         # descargar módulo
modprobe -v nombre         # cargar con verbose (ver qué hace)

insmod /ruta/modulo.ko     # cargar fichero .ko directamente (sin resolver deps)
rmmod nombre               # descargar (sin resolver deps)

# Carga automática en boot
echo "nombre_modulo" >> /etc/modules-load.d/modulo.conf

# Parámetros de módulos
/etc/modprobe.d/*.conf
echo "options iwlwifi 11n_disable=1" > /etc/modprobe.d/wifi.conf

# Módulos disponibles para el kernel actual
ls /lib/modules/$(uname -r)/kernel/
💡
modprobe vs insmod: usa siempre modprobe. Resuelve dependencias automáticamente (si el módulo A necesita el módulo B, lo carga también). insmod es de bajo nivel y fallará si las dependencias no están cargadas.

Journaling — protección contra corrupción

El journaling es un mecanismo de los sistemas de ficheros para garantizar la integridad de los datos ante fallos inesperados (corte de luz, kernel panic…).

¿Cómo funciona?

Antes de escribir datos en el disco, el sistema anota la operación pendiente en un área especial llamada journal (diario). El proceso es:

  1. Escribir la intención de la operación en el journal.
  2. Ejecutar la operación real en el disco.
  3. Marcar la entrada del journal como completada.

Si el sistema falla en el paso 2, al reiniciar el kernel lee el journal, detecta la operación incompleta y la completa o deshace. Sin journaling, una escritura incompleta puede dejar el filesystem en estado inconsistente.

Niveles de journaling en ext4

  • journal: registra datos Y metadatos. Máxima protección, más lento.
  • ordered (por defecto): solo metadatos, pero garantiza que los datos se escriben antes. Buen equilibrio.
    • writeback: solo metadatos, sin garantía de orden. Más rápido, menos seguro.

COW — Copy On Write

Copy-on-Write es una estrategia usada por Btrfs y ZFS donde al modificar un bloque de datos, en lugar de sobreescribirlo, se escribe la nueva versión en un bloque nuevo y se actualiza el árbol de metadatos para apuntar al nuevo bloque. El bloque original permanece intacto hasta que se libera.

  • Ventaja: los snapshots son instantáneos y casi gratuitos (solo se copia lo que cambia).
  • Ventaja: permite detectar corrupción silenciosa mediante checksums.
  • Ventaja: el sistema nunca está en estado inconsistente (o tienes la versión vieja, o la nueva, nunca a medias).
  • Inconveniente: fragmentación a largo plazo, overhead en escrituras aleatorias.

Montaje automático — /etc/fstab

Para que un filesystem se monte automáticamente en cada arranque, hay que añadir una entrada en /etc/fstab.

# Formato: <dispositivo>  <punto-montaje>  <tipo>  <opciones>  <dump>  <pass>
UUID=7e32f35e-ab12   /              ext4    defaults        0       1
UUID=a1b2c3d4-ef56   /boot          xfs     defaults        0       2
UUID=f0e1d2c3-b4a5   /home          ext4    defaults        0       2
UUID=11223344-5566   swap           swap    defaults        0       0
tmpfs                /tmp           tmpfs   defaults,noatime,size=2G  0  0

Campo dump (5º campo)

Indica si el programa dump (herramienta antigua de backup) debe respaldar este filesystem.

  • 0 — No hacer backup con dump (valor habitual hoy)
  • 1 — Hacer backup con dump

Campo pass (6º campo)

Determina el orden en que fsck comprueba la integridad de los filesystems al arrancar.

  • 0 — No comprobar (swap, tmpfs, filesystems de red)
  • 1 — Comprobar primero (reservado para / — raíz)
  • 2 — Comprobar después de los "1" (resto de particiones locales)
# Identificar dispositivos por UUID (más estable que /dev/sdX)
blkid
lsblk -f

# Probar /etc/fstab sin reiniciar
mount -a   # monta todo lo que esté en fstab y no esté montado

# Montar/desmontar manualmente
mount -t ext4 /dev/sdb1 /mnt/datos

lsof para liberar un punto de montaje

Si umount falla con "device is busy", significa que hay procesos usando ficheros en ese filesystem.

# Ver qué procesos tienen abiertos ficheros en /mnt/datos
lsof /mnt/datos
lsof +D /mnt/datos   # recursivo

# Ver qué proceso está usando un fichero concreto

fuser -v /mnt/datos    # solo listar (sin matar)

# Ahora se puede desmontar
umount /mnt/datos

# Unmount lazy (espera a que terminen los procesos)
umount -l /mnt/datos   # desconecta el filesystem pero permite que los procesos terminen

Inodo — metadatos del fichero

Cada fichero tiene un inode que almacena: tipo, permisos, UID/GID, timestamps (atime, mtime, ctime), tamaño y punteros a bloques de datos. El nombre del fichero NO está en el inode, está en el directorio que lo contiene.

ls -li          # ver número de inode
stat fichero    # todos los metadatos del inode
df -i           # inodos disponibles/usados por filesystem

Enlace duro vs Enlace simbólico

Enlace duro (Hard link)

Crea una nueva entrada de directorio apuntando al mismo inode. El fichero tiene dos (o más) nombres.

  • Mismo inode → mismos datos, mismos metadatos, mismos permisos.
  • El fichero real solo se borra cuando el contador de enlaces llega a 0.
  • No puede apuntar a directorios (evita ciclos).
  • No puede cruzar filesystems distintos (el inode es local al FS).
ln fichero_original enlace_duro
ls -li  # mismo inode, nlink=2

Enlace simbólico (Soft link / Symlink)

Crea un fichero nuevo cuyo contenido es la ruta del objetivo. Es como un acceso directo.

  • Inode propio y distinto al del objetivo.
  • Si se borra el objetivo, el enlace queda roto (dangling symlink).
  • Puede apuntar a directorios.
  • Puede cruzar filesystems y particiones.
  • Los permisos del symlink no importan; lo que cuenta son los del destino.
ln -s /ruta/objetivo nombre_enlace
ls -la  # muestra → /ruta/objetivo
readlink -f enlace  # resolver ruta real

Sticky bit — ¿qué hace exactamente?

El sticky bit en un directorio indica que, aunque cualquier usuario pueda crear ficheros en él (si tiene w sobre el directorio), solo el propietario del fichero puede borrarlo o renombrarlo.

El ejemplo clásico es /tmp: todos los usuarios pueden crear ficheros temporales, pero nadie puede borrar los ficheros de otro usuario.

ls -ld /tmp
drwxrwxrwt 10 root root  # la 't' al final = sticky bit activo

chmod +t directorio     # activar sticky bit
chmod 1777 directorio   # rwxrwxrwx + sticky = 1777
ℹ️
Históricamente el sticky bit en ficheros ejecutables indicaba "mantener en swap después de ejecutar". Hoy en día ese comportamiento está obsoleto; el sticky bit solo tiene efecto sobre directorios.

Directorios como ficheros — permisos

En Linux, todo es un fichero, incluidos los directorios. Un directorio es un fichero especial cuyo contenido es una tabla de pares (nombre → número de inode). Por eso también tienen permisos rwx, pero con significado distinto:

PermisoSobre fichero regularSobre directorio
r (4)Leer contenido del ficheroListar el contenido (ls)
w (2)Modificar el ficheroCrear, borrar o renombrar ficheros dentro
x (1)Ejecutar como programaEntrar al directorio (cd), acceder a ficheros dentro
⚠️
Caso tricky: si tienes r pero no x sobre un directorio, puedes listar los nombres de los ficheros pero no acceder a ellos ni ver sus metadatos. Si tienes x pero no r, puedes acceder a ficheros si conoces su nombre exacto, pero no puedes listarlos.
# Permisos habituales
chmod 755 directorio  # rwxr-xr-x: propietario todo, resto leer+entrar
chmod 700 directorio  # rwx------: solo el propietario
chmod 644 fichero     # rw-r--r--: propietario leer+escribir, resto solo leer
umask 022             # máscara: dirs=755, ficheros=644

LVM — Logical Volume Manager

PV (Physical Volume) → varios PVs se agrupan en un VG (Volume Group) → el VG se divide en LVs (Logical Volumes) → cada LV se formatea con un FS y se monta.

# Flujo completo
pvcreate /dev/sdb                     # inicializar disco como PV
vgcreate mi_vg /dev/sdb               # crear VG
lvcreate -L 100G -n datos_lv mi_vg   # crear LV de 100GB
mkfs.ext4 /dev/mi_vg/datos_lv        # formatear
mount /dev/mi_vg/datos_lv /datos     # montar

# Extender sin desmontar
pvcreate /dev/sdc
vgextend mi_vg /dev/sdc
lvextend -l +100%FREE /dev/mi_vg/datos_lv
resize2fs /dev/mi_vg/datos_lv        # ext4
xfs_growfs /datos                    # XFS

pvs; vgs; lvs                        # estado

Quotas de disco — soft y hard limit

Las quotas permiten limitar el espacio en disco que puede usar cada usuario o grupo.

Soft limit

Límite "blando". El usuario puede superarlo temporalmente durante un período de gracia (normalmente 7 días). Si no reduce el uso antes de que expire, el soft limit se convierte en hard limit.

Sirve como aviso: el sistema le notifica que está cerca de su límite.

Hard limit

Límite "duro". No se puede superar bajo ninguna circunstancia. Si el usuario intenta escribir más datos una vez alcanzado el hard limit, recibe un error "Disk quota exceeded" y la operación falla.

# 1. Añadir opciones en /etc/fstab para /home:
#    UUID=xxx /home ext4 defaults,usrquota,grpquota 0 2
mount -o remount /home
quotacheck -uvgm /home          # crear ficheros de cuota
quotaon -uvga                   # activar cuotas

# Establecer cuotas de usuario
# setquota -u usuario soft_bloques hard_bloques soft_inodos hard_inodos mountpoint
setquota -u usuario 100M 120M 100 120 /home
# → soft=100MB hard=120MB (bloques) soft=100 hard=120 (inodos)

edquota -u usuario              # editar cuota interactivamente
quota -s usuario                # ver uso actual del usuario
repquota /home                  # informe de todas las cuotas de /home

Backup

Regla 3-2-1-1-0

  • 3 copias de los datos
  • 2 medios de almacenamiento diferentes (NAS + nube, HDD + cinta…)
  • 1 copia fuera de las instalaciones (offsite)
  • 1 copia inmutable o air-gapped (no modificable por ransomware)
  • 0 errores verificados al restaurar (¡probar siempre!)

RPO (Recovery Point Objective): máxima pérdida de datos aceptable (tiempo desde el último backup). RTO (Recovery Time Objective): máximo tiempo tolerable para restaurar el servicio.

Tipos de backup

Snapshot vs Backup Full

Snapshot: usa COW para capturar el estado del filesystem en un instante. Es casi instantáneo y ocupa poco espacio inicialmente (solo almacena los bloques que cambian posteriormente). Vive en el mismo disco que los datos originales — no protege contra fallo de hardware.

Backup Full: copia todos los datos a un medio separado. Lento y ocupa mucho espacio, pero protege contra fallo del disco original, borrado accidental y desastres.

→ Los snapshots complementan los backups pero no los reemplazan.

Estrategia combinada típica

  • Snapshot cada hora (para recuperación rápida de ficheros borrados)
  • Backup incremental diario (a NAS o nube)
  • Backup full semanal (a cinta o almacenamiento offsite)
  • Verificación de restore mensual

rsync — sincronización eficiente

rsync (Remote Sync) es ideal para backups incrementales porque solo transfiere los bloques que han cambiado, no los ficheros completos. Compara origen y destino mediante checksums y tamaño/fecha.

¿Cuándo usar rsync?

  • Backups incrementales diarios donde los datos cambian poco.
  • Sincronizar directorios entre servidores.
  • Migrar datos entre máquinas preservando permisos y timestamps.
  • Cuando se necesita reanudar transferencias interrumpidas.
# Sincronización local
rsync -av /home/ /backup/home/             # básica
rsync -avz /home/ /backup/home/            # con compresión en tránsito
rsync -av --delete /home/ /backup/home/   # borrar en destino lo que no está en origen

# Sincronización remota por SSH
rsync -avz -e ssh /home/ user@servidor:/backup/home/
rsync -avz -e "ssh -p 2222" /home/ user@servidor:/backup/

# Opciones avanzadas
rsync -av --dry-run /home/ /backup/       # simulación sin cambios reales
rsync -av --progress /home/ /backup/      # ver progreso de cada fichero
rsync -av --bwlimit=5000 /home/ /backup/  # limitar ancho de banda (5 MB/s)
rsync -av --exclude="*.tmp" /home/ /bck/  # excluir ficheros
rsync -av --backup --backup-dir=/bck/old /src/ /dst/  # mover sobreescritos a old/
